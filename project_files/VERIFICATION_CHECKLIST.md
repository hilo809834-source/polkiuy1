## Patterns already caught once — don't repeat them


These describe specific bugs found in an earlier build attempt of this same project, kept here as concrete examples of exactly the kind of thing `RULES.md` exists to prevent. If you're starting from an empty repo, none of these files exist yet — that's expected, not a problem to solve. The point is the pattern, so watch for its shape while writing the equivalent code fresh, not these exact file paths:


- A background build function whose body did nothing (`...`) while the rest of the system treated it as implemented.
- A database call missing `await`, silently returning an unawaited coroutine instead of real data, with nothing catching it.
- Security scanners that returned "passed" unconditionally without actually scanning anything.




## Phase 1 — Scaffolding & secrets
- A deliberately planted fake secret in a source file gets caught by a real check before it would reach a commit or a log line.
- Evidence required: the actual secret(s) planted, and the actual detector output showing each one caught.


## Phase 2 — Model router
- A real call succeeds against two different real providers.
- Evidence required: the actual response text from each provider, pasted directly, not summarized or described.


## Phase 3 — Sandbox execution
- A deliberately runaway script actually gets killed by the timeout/memory limit.
- Evidence required: the actual exit code, duration, and kill reason from a real run. A normal script completing successfully is not sufficient evidence on its own — the limit itself has to be shown working.


## Phase 4 — Minimal orchestrator
- A hardcoded "hello world" task goes from a text prompt to a running process inside the sandbox, end to end, through the router — as one connected flow, not as separately verified pieces.
- Evidence required: one real run showing the task go in, a real router call happen, and real sandboxed output come back, in that order, in a single execution. Phases 1-3 each passing on their own is necessary but not sufficient here — this phase is specifically about them working together.


## Phase 5 — Intake & specification
- A real free-text idea produces a real structured spec and real tiered questions from an actual model call — not a hardcoded example response.
- Evidence required: the actual idea text submitted, and the actual spec and questions the model produced from it.


## Phase 6 — Core build loop
- Given a simple greenfield spec, the system produces working code that passes acceptance criteria it did not write itself, end to end, with no human editing code.
- Evidence required: a project ID, the actual generated code, and the actual test output run against it.


## Phase 7 — Quality loop

## Phase 8 — Security, compliance & tool connections

- Evidence required: actual scanner output (even if the finding is "no issues" — that's a real finding too), and a real repo actually imported, not a mocked response.


## Phase 9 — Delivery & cost guardrails
